# Accessibility & performance for anirach.com

This site has no build step, no partials and no tests. Every page in `blog/` carries
its own `<style>`, its own `:root` and its own copy of the nav. A "global" fix is an
N-file edit, and nothing catches a regression except you. That is why these rules are
written as concrete values you can paste, not principles you have to re-derive.

Everything below was measured on this repo. Re-run the command if you doubt a number.

> ## Standing rule — numbers in this skill are load-bearing
>
> **Any change that invalidates a number in a skill file must update that number in
> the same commit.** This file exists to save the next session from re-deriving
> measurements; a confidently wrong measurement is worse than none, because it gets

## Standing rules — apply when writing or editing any page

### 1. Covers ship as JPEG at ≤200 KB. Never PNG. **[DONE — hold the line]**

`ec2827b` re-encoded the 15 oversized PNG covers to JPG and `21c8a55` re-ran the four
that still cleared 200 KB at `formatOptions 70`; the three 2026-08-23 book covers shipped
compliant, and the 20 AI Transformation covers were drawn compliant on 2026-09-05. Today
there are **0 PNG covers and 132 JPG covers — 124 `*-cover.jpg` (avg 43 KB, largest 61 KB)
plus 8 suffixed book faces (avg 86 KB, largest 174 KB) — none over 200 KB.**

```bash
ls images/*-cover.png 2>/dev/null | wc -l                     # → 0
find images -name '*-cover.*' -size +200k                     # → nothing
ls -l images/*-cover.jpg | awk '{s+=$5;n++} END {print n" jpg, avg "int(s/n/1024)" KB"}'
# → 77 jpg, avg 42 KB    (unsuffixed only — see the blind spot below)
```

**`images/` holds 308 files / 17 MB in four classes. Know which one you are touching:**

| Class | Count | Shape | Weight | Format |
|---|---|---|---|---|
| post + book covers `<slug>-cover.jpg` | 77 (+8 suffixed faces) | 800×800 (the Springer jacket 306×461; book faces portrait) | avg 42 KB, max 54 KB | JPEG, ≤200 KB |
| share cards `<slug>-og.jpg` | 80 | 1200×630 exactly — INV-27 reads the real header | avg 61 KB, max 83 KB | JPEG |
| **series figures `ai-transformation-fig-*.png`** | **19** | **1400 px wide, 560–1000 tall** | **avg 44 KB, max 58 KB** | **8-bit palette PNG** |
| legacy diagrams `*-arch/-flow/-levels.png` | 5 | mixed | 123–235 KB | PNG |

The **19 series figures** (2026-09-05, `scripts/make_figure.py`) are the newest class and the
one most likely to be got wrong. They are *palette* PNGs, not truecolour — flat fills, hard
edges and a fixed 11-token palette compress to an average 44 KB at 1400 px, which is why
they beat a JPEG of the same drawing and why re-saving one through `sips` as truecolour
will roughly triple it. Regenerate with `make_figure.py`; never hand-edit a figure PNG.
The other reason they are cheap: 17 posts carry one or two, and every one is
`loading="lazy" decoding="async"` with explicit `width`/`height`, so none of them is on any
critical path.

```bash
ls -l images/ai-transformation-fig-*.png | awk '{s+=$5;n++} END {print n" figs, avg "int(s/n/1024)" KB"}'
# → 19 figs, avg 44 KB
ls -l images/*-og.jpg | awk '{s+=$5;n++} END {print n" og, avg "int(s/n/1024)" KB"}'
# → 127 og, avg 61 KB
```

Before adding a cover, run `ls -lS images/ | head` and compare. Hard-fail any cover
over 200 KB. To produce one:

```bash
sips -s format jpeg -s formatOptions 70 -Z 1600 new-cover.png --out images/new-cover.jpg
```

PNG is correct for the five *diagram* images only — `*-arch.png`, `*-flow.png`,
`*-levels.png` — which are right at 123–235 KB. Do not convert those; PNG preserves the
crisp lines that a JPEG smears. (Diagrams are PNG for a reason: inline HTML/CSS and
ASCII-art diagrams were tried and reverted in f4f7e1b, 4fc85af, c270892 and 4ae2660
because they kept breaking layout.)

**Blind spot in the census above:** the eight paired book faces —
`one-day-of-light-cover-en/-th.jpg` (67 KB each), `a-pocketful-of-questions-cover-en/-th.jpg`
(73 / 77 KB), `the-thirteenth-seal-cover-en/-th.jpg` (54 / 62 KB) and
`three-old-men-cover-front/-back.jpg` (175 / 120 KB) — end in `-cover-<face>.jpg` and so match
neither the `*-cover.jpg` ls nor the `*-cover.*` find. Audit them with
`ls -l images/*-cover-*.jpg` (→ 8 files, avg 86 KB, all compliant).

**Downloadable PDFs live in their section's directory** (the
`books/one-day-of-light-en.pdf` pattern), **≤10 MB each, metadata set (Title/Author)**.
`check_site.py` INV-05 verifies each PDF `href` resolves; **no orphan scan covers PDFs**
— INV-06a reads `images/` only — so every PDF must stay referenced, and removing a page
removes its PDFs in the same commit.

### 2. Every `<img>` gets `width`, `height`, `loading` and `decoding`. **[DONE — hold the line]**

**355 of 355 real `<img>` tags carry all four** (a whole-file regex reports 392 — the extra 37
are a literal `<img>` inside a CSS comment in 37 posts, not tags), since `e8da9da` (the books/publications pages
and `books/one-day-of-light.html` shipped compliant). 83 also carry
`fetchpriority`. This and `alt` coverage are the only two 100%-complete practices on the
site; a new post that omits them is a regression, not a gap.

```bash
python3 - <<'EOF'
import re, pathlib
n=ok=0
for p in pathlib.Path('.').rglob('*.html'):
    if '.claude' in p.parts or '.git' in p.parts: continue
    for m in re.finditer(r'<img\b[^>]*>', p.read_text(encoding='utf-8'), re.S):
        n+=1; ok+= all(a+'=' in m.group(0) for a in ('loading','decoding','width','height'))
print(ok, "/", n)          # → 299 / 336
EOF
```

**Use that multiline parse, not `grep -oh "<img[^>]*>"`** — the line-based grep reports
316 against the parse's 336, because 20 `<img>` are written across multiple lines (mostly on the
books/publications pages). Both totals also count a literal `<img>` written inside a CSS comment in
37 posts, which is not a tag: **the real tag count is 299, and all 299 are compliant.** Quoting
316, or 336, where the answer is 299 is exactly the kind of small wrongness that makes a reader
stop trusting this file.

**Bilingualisation doubles every in-body `<img>`, and that is by design.** Each post holds
its article twice — `<div class="l-th">` and `<div class="l-en" lang="en">` — so the 19
series figures appear as **38 `<img>` tags across 17 posts**, one per language track, each
with its own translated `alt`. Two consequences when you touch a figure: the attribute fix
you make in one track must be made in the other (`python3 scripts/bilingualize.py --verify
<slug>` is what catches a one-track edit), and a per-post `<img>` count that looks doubled
is correct, not a duplication bug. The hero cover and the card image are *not* duplicated —
they sit outside both tracks.

The figure markup is fixed; copy it rather than inventing one:

```html
<figure class="figure">
  <a href="../images/ai-transformation-fig-s1-six-layers.png">
    <img class="figure__img" src="../images/ai-transformation-fig-s1-six-layers.png"
         alt="…a full sentence describing the diagram, in this track's language…"
         width="1400" height="840" loading="lazy" decoding="async">
  </a>
  <figcaption class="figure__caption">…</figcaption>
</figure>
```

The wrapping `<a>` (full-size PNG) has no text of its own, so **the `alt` is the link's
entire accessible name** — a bare `alt="diagram"` would produce a link announced as
"diagram, link" and nothing else. The shipped alts are full sentences naming the parts;
match that. `width`/`height` are the figure's real pixel size (`1400 × 560–1000`), never
the rendered width — `.figure__img` is `width: 100%; height: auto`.

Card images in `blog/index.html` sit in a 352×220 CSS px slot (1200px section −
2×2.5rem padding = 1120; `repeat(auto-fill, minmax(340px,1fr))` with `gap:2rem` →
3 cols of 352px; `.card__image { aspect-ratio: 16/10 }` → 220px). Source covers are **800×800 on all 76 post covers** (the 77th `*-cover.jpg` is the Springer jacket, `libraries-in-transformation-cover.jpg` at 306×461) as of 2026-08-26 — the drawn cover
system (`scripts/make_cover.py` + `scripts/covers.tsv`) replaced 35 AI clip-art
images at mixed canvases (1024×1024, 1024×680, 800×446, …) with one. `object-fit:
cover` into the 16:10 slot throws away 37.5% of a square source, which is why the
renderer keeps every glyph and every motif inside a SAFE BAND of y∈[0.20,0.80],
x∈[0.12,0.88]; the crop eats only ground. Check
the actual file with `sips -g pixelWidth -g pixelHeight` before quoting a waste figure.

```html
<!-- blog/index.html card: below the fold, fixed slot -->
<img src="../images/openclaw-101-cover.jpg" alt="" width="800" height="800"
     loading="lazy" decoding="async">

<!-- post hero cover: above the fold, do NOT lazy-load the LCP element -->
<img src="../images/openclaw-101-cover.jpg" alt="OpenClaw 101 architecture overview"
     width="800" height="800" loading="eager" fetchpriority="high" decoding="async">
```

`width`/`height` are the **source** pixel size, not the CSS slot size — that is the
convention already on disk (the live card for this cover writes `1024`×`1024`), and it
is what makes the intrinsic aspect ratio correct. Get it from
`sips -g pixelWidth -g pixelHeight images/<file>`. **Every cover is `.jpg` now**; there
are no `-cover.png` files left.

### 3. No page may ship a control that needs JavaScript — there is no JavaScript. **[ENFORCED]**

**The old version of this rule said "`index.html` is still the only file on the site with a
`<script>`". That has been false since 2026-08-26**, when `bb9c7dc` deleted `script.js` and
made the site zero-JavaScript. `check_site.py` **INV-38** now fails the build on any
`<script>` that is not `application/ld+json`, so "no JS" is a gate, not a preference.

`<script>` does appear on 79 pages, and every one is data:

```bash
grep -rhoE '<script[^>]*>' --include="*.html" --exclude-dir=.claude .
# → 79 × <script type="application/ld+json">    …and nothing else
```

That is the schema.org block (`index.html`, two `books/` detail pages, and a BlogPosting on
all 83 posts). The browser parses it and never executes it. **INV-38's whitelist regex
requires double quotes around the type** — `type='application/ld+json'` fails the build.

Nothing was lost by the deletion, because each of the script's four jobs has a CSS
replacement in `style.css` (reveal → `animation-timeline: view()`; scrolled nav →
`animation-timeline: scroll(root)`; hamburger → `.nav__links:target`; smooth scroll →
`scroll-behavior`). Do not reach for JavaScript to restore any of them, and never
"complete" the `from`-only `@keyframes reveal` with a `to` — the missing `to` is what makes
an element's resting state its natural state on a browser with no `animation-timeline`.

**Two pure-CSS menu mechanisms exist, both correct; match the one the file already uses.**

| Mechanism | Files | Markup |
|---|---|---|
| `.nav__links:target` + `.nav__hamburger` | `index.html` only | anchor-driven, `style.css:172` |
| `.nav__toggle` checkbox + `.nav__burger` label | **11 section-chrome pages** — `404.html`, `blog/index.html`, `thoughts/index.html`, `books/index.html` + the 4 `books/*.html` detail pages, `news/`, `projects/`, `publications/` (takeover 950px since 2026-09-08) | hidden `<input type="checkbox" id="navToggle" class="nav__toggle">`, `<label for="navToggle" class="nav__burger">☰</label>`, and `.nav__toggle:checked ~ .nav__links { display: flex; }` inside the **800px** media query (moved up from 768px in `5178252`: the 6-link desktop bar broke in the 769–771px band) |

`.nav__toggle:focus-visible + .nav__burger` gives the label a visible ring, so both are
keyboard-operable. `check_site.py` INV-12 ("every menu-toggle control is wired: JS toggles
need `<script>`, CSS toggles need their label+checkbox pair") PASSes today with **no
baseline entry**.

The other 76 files — every post — carry no menu at all: their nav links stay visible and
shrink at narrow widths. That is the third correct answer, and the one a new post should
copy. Never ship a `<button class="nav__hamburger">` outside `index.html`.

```bash
grep -rl 'class="nav__burger"' --include="*.html" --exclude-dir=.claude . | wc -l   # → 10
```

### 4. `--blue #226299` is a TEXT colour now. `--blue-light` is borders only. **[RE-KEYED 2026-08-26]**

> **`.post-series-footer` and `.post-hero__meta` are DONE (2026-08-26, whole-site Phase 1),
> and have stayed done through two more series.** The 22 `.post-series-footer` rules that read
> `var(--gray)` at 2.40:1 became `var(--slate-light)` (5.91:1); the count is **61 rules today,
> all `var(--slate-light)`, zero `var(--gray)`**. The 24 `.post-hero__meta` rules that read
> `rgba(255,255,255,0.6–0.95)` became `#fff`; today it is **44 `#fff` on the 43 Deep Blue posts
> (6.41:1 at the worst stop) and 32 `var(--slate-light)` on the 33 Sunrise posts (4.83:1 at the
> worst stop)**. R3 and R4's paragraphs below are HISTORY.

**This rule inverted on 2026-08-26.** The palette was re-keyed to the book covers, and the token
that used to be the site's largest a11y defect now passes everywhere: `--blue #226299` is 6.41:1 on
white, 5.99 on the `--bg` cream, 5.09 on cloud and 4.90 on parchment — links, chips and small text
are all legal. `--blue-dark #1a4d7a` is 8.80:1 and stays the hover/pressed state.

**Three roles need care, all verified live:**
- `--blue-light #4992b9` is **borders only** (3.45:1 on white, 3.94 on navy). Its 32 former uses
  were all footer link text; they moved to `--gold` (5.73:1 on the new navy).
- The focus ring carries `outline-offset: 3px`, so it lands on the *page* ground. Inside a navy
  footer `--blue` collapses to 2.12:1, so a 28th token exists: `--focus`, re-pointed by
  `.footer, .blog-footer, pre { --focus: var(--gold) }` in all 87 files.
- **`--coral #c2410c` — the 30th token, added 2026-09-05 with AI Transformation. It is a
  ground-dependent colour and the one most likely to be misused.** Measured: **5.18:1 on
  white** and **4.84:1 on `--bg` cream** (body copy is legal on both), but only **4.11:1 on
  `--cloud`**, **3.95:1 on `--parchment`** and **4.10–4.55:1 on the five figure tints**. On a
  tint or on either brand ground it is **large-text-or-graphics only** (the 3:1 bar), never
  body copy. Note also that all 20 AI Transformation posts *declare* `--coral` and **none of
  them uses `var(--coral)` in CSS** — it exists so the token table and
  `scripts/make_figure.py`'s `CORAL = (194, 65, 12)` stay in sync, and the colour is actually
  spent inside the drawn covers and figures. Full table in `references/contrast.md` §A.

Historical, for context — the old value's failures, which is why the re-key happened:
`--blue #6366f1` failed WCAG AA in **every** light-background use: 4.47:1 on white,
4.09:1 on the tag chip, 3.87:1 on the series-count chip, 3.90:1 and 2.99:1 on the two
ends of the old hero gradient.
At the time `var(--blue)` was used 279 times against `var(--blue-dark)`'s 60, and every
*text* use among them was a fail. Today's counts — **636 `var(--blue)`, 230
`var(--blue-dark)`, 321 `var(--gold)`, and just 6 `var(--blue-light)`** — carry no such
implication, because `--blue` passes as text now. The collapse of `--blue-light` from 38 uses
to 6 is the re-key working: it is borders-only, and the footer link text that used to carry it
moved to `--gold`.

That gradient no longer exists either — the light family is now the sunrise
`#eef3f3 → #dee7e6 → #e9e1c4`, on which `--navy` measures 10.4–12.1:1. `references/contrast.md`
was rewritten to the current palette on 2026-09-06 and is the authority for every pair.

### 5. A visible focus ring exists everywhere. **[DONE]** Hover/focus parity **[DONE 2026-08-26]**

`e8da9da` installed this block; every page added since has shipped with it. Today it is in
**134 embedded `<style>` blocks + `style.css`** = all **135** pages, with the gold re-point
scoped to the two surfaces where the blue ring collapses:

```css
:focus-visible { outline: 2px solid var(--focus); outline-offset: 3px; border-radius: 2px; }
.footer, .blog-footer, pre { --focus: var(--gold); }   /* --blue is 2.12:1 on navy */
:focus:not(:focus-visible) { outline: none; }
```

```bash
grep -rL ':focus-visible' --include='*.html' --exclude-dir=.claude . ; grep -L ':focus-visible' style.css
# → index.html only, and correctly so: its CSS is style.css.
```

**Two things this changes about how you must report focus problems.**

1. **`outline: none` now exists, 87 times, and it is correct.** It is scoped to
   `:focus:not(:focus-visible)`, i.e. it suppresses the ring for mouse and programmatic
   focus only, never for keyboard. The old advice in this file — "`outline` is never set
   to `none` anywhere, verify before claiming a focus failure" — will now find 87 matches
   and mislead you into the opposite error. Read the selector, not the declaration.
2. **Parity landed 2026-08-26.** There are **548 `:hover` rules** across the site (the old
   figures of 144 and 227 were both undercounts of a site that has since doubled).
   `.card:focus-within` mirrors the lift, the image scale and the colour shift on the **6
   files that actually have cards** — `blog/`, `books/`, `news/`, `projects/`,
   `publications/` and `404.html` — plus `.research__card` / `.projects__card` in
   `style.css`, so a keyboard user gets the same affordance a mouse user does.

**`assets/a11y-block.css` is now fully landed** — every rule it holds is on disk
(`.card:focus-within` in the 6 card-bearing files, `.skip-link` in 86 files + `style.css`,
and `[data-reveal] { opacity: 1 !important }` at `style.css:902`). Its own header still
describes a 47-file site; read it as a record of what shipped, not as a to-do list, and do
**not** paste it into a page again — a second, differently-worded focus ring would fork the
one rule the whole site agrees on.

### 6. Text on a hero must clear AA against the gradient's **worst** stop. **[DONE — hold the line]**

**Solved structurally, not pair-by-pair.** The 2026-08-26 reheroize collapsed 10 hero
gradients down to **2 families**, and `check_site.py` **INV-28** fails the build on any
`.post-hero` background that is neither:

| Family | Gradient | Posts | Meta colour | Worst-stop ratio |
|---|---|---|---|---|
| **Deep Blue** | `135deg, #11304b 0%, #1a4d7a 45%, #226299 100%` | 43 | `#fff` (44 rules) | **6.41:1** on `#226299` |
| **Sunrise** | `135deg, #eef3f3 0%, #dee7e6 50%, #e9e1c4 100%` | 33 | `var(--slate-light)` (32 rules) | **4.83:1** on `#e9e1c4` |

No scrim is needed on either, and there are **zero** `rgba(255,255,255,0.x)` meta colours
left. The old rule's whole point survives as a constraint on *new* work: if you invent a
third family, the text has to clear 4.5:1 against its lightest stop for white text or its
darkest stop for dark text — and INV-28 will fail you before you find out the hard way.

```bash
python3 -c "
import re,glob,collections
c=collections.Counter()
for f in glob.glob('blog/*.html'):
    for m in re.finditer(r'\.post-hero__meta\s*\{([^}]*)\}', open(f,encoding='utf-8').read()):
        cm=re.search(r'color:\s*([^;]+)', m.group(1)); c[cm.group(1).strip() if cm else 'none']+=1
print(dict(c))"          # → {'#fff': 44, 'var(--slate-light)': 32, 'none': 71}
```

### 7. Thai page, English headings — mark the switch. **[STILL OPEN: 250 headings]**

**83 of 94** files are `<html lang="th">` — all 83 posts. The 11 `en` files are the landing
page, the 5 section indexes, the 4 `books/` detail pages and `404.html`. The page-level
`lang` **cannot flip** on a post: the TH ⇄ EN switch is pure CSS, and CSS cannot rewrite an
attribute. `check_site.py` INV-13 enforces the page-level split.

**What bilingualisation did and did not fix.** Every post now carries a
`<div class="l-en" lang="en">` wrapper around its whole English track, plus ~3 `<span
class="l-en" lang="en">` pairs on the `<h1>`, hero sub and series footer — 335 `lang="en"`
elements across the posts. That correctly voices the *English track*. It does nothing for
the English **inside the Thai track**, which is where the original defect lives:

```
English-only <h2>/<h3>/<h4> headings inside the l-th track:  250
…of those carrying lang="en":                                  0
```

A Thai screen-reader voice reading "OAuth Implementation with Passport.js" is
unintelligible, and there are 250 of them. The 11 `en` pages do the mirror-image job right —
they wrap their Thai passages in `<span lang="th">` (276 switches across 10 files). Nothing
enforces the inline switch in either direction.

```bash
grep -rhoE '<html lang="[^"]*"' --include="*.html" --exclude-dir=.claude . | sort | uniq -c
# → 11 en, 76 th
```

```html
<h2 lang="en">Kubernetes Orchestration</h2>
<pre lang="en"><code>kubectl apply -f deploy.yaml</code></pre>
```

**Fix it in both tracks or not at all.** A heading edited only in `.l-th` leaves the two
copies out of step; `python3 scripts/bilingualize.py --verify <slug>` is the check that
catches it.

### 8. One `<h1>`, no level skips, content in `<main id="main">`. **[LANDMARK DONE — 31 skips left]**

|---|---|---|

`width`/`height` stay the **source** size (800×800), per rule 2 — both candidates are square,
so the intrinsic ratio is right and nothing shifts.

### R8b. **Request a variable font with the RANGE syntax, or you get static instances.** [FIXED 2026-09-10]

**The previous version of this rule was wrong, and it was expensive.** It said Google Fonts
serves Inter and JetBrains Mono as variable fonts, so `wght@300;400;…;900` and `wght@400`
cost the same bytes. That is true of the *font*, not of the *request*. The CSS2 API keys on
punctuation:

| syntax | what Google serves |
|---|---|
| `wght@300;400;500;600;700;800;900` (semicolons — discrete) | **7 static instances**, one file each |
| `wght@300..900` (two dots — a range) | **1 variable file** covering the whole axis |

Measured 2026-09-10 against the live API, Inter's `latin` subset:

```
wght@300;400;500;600;700;800;900   ->  7 files, 331.1 KB
wght@300..900                      ->  1 file,   47.3 KB
```

The site had shipped the semicolon form on every page since the fonts were introduced. A
bilingual essay page, which uses Inter weights 400–800, was downloading **five** 47.3 KB
Inter files where one would do. Fixed on 2026-09-10 across all 136 HTML files plus
`scripts/build_series.py`:

```
Inter:wght@300;400;500;600;700;800;900  ->  Inter:wght@300..900
JetBrains+Mono:wght@400;500;600         ->  JetBrains+Mono:wght@400..600
Sarabun:wght@400;500;600;700;800        ->  unchanged — see below
```

Per-page font payload for a Thai essay (thai + latin subsets, the weights actually used):

| | files | KB |
|---|---|---|
| before | 15 | 340.5 |
| after | 10 | 151.3 |

**189 KB saved per page, 56% of the font bytes**, on every one of the 136 pages. A page with
code blocks saves a further 61 KB, because JetBrains Mono went 3 files → 1.

**Sarabun has no variable version and must keep the semicolon form.**
`family=Sarabun:wght@400..800` returns **HTTP 400**. Its five weights are five real static
files (~11 KB latin + ~9.5 KB thai each) and all five are used — see the census below. Do
not "tidy" Sarabun into range syntax; you will get an error page instead of a stylesheet.

**How to check a new page in one command:**

```bash
grep -o 'Inter:wght@[^&]*' <file>          # must print Inter:wght@300..900, never a semicolon list
```

### R8. Sarabun's five weights — **the real defect, fixed 2026-08-26**

**Sarabun is the one that mattered, and it is static.** An unrequested weight is *synthesised* by
the browser — faux-bold, which smears Thai glyphs far more visibly than Latin ones. The site
declared:

| Weight | Declarations | Was loaded? |
|---|---|---|
| 400 | 6 | yes |
| 500 | 43 | **no — synthesised** |
| 600 | 407 | yes |
| 700 | 330 | yes |
| 800 | 122 | **no — synthesised** |

Fixed on 2026-08-26 and now on **all 87 pages** (the 2026-09-03 bilingual sweep and the
2026-09-05 series launch both shipped it):

```
Sarabun:wght@400;600;700   ->   Sarabun:wght@400;500;600;700;800
```

Verified in the browser with `document.fonts`: five real Sarabun faces now load where three did.
The declaration census that motivated it has grown with the site and still justifies the five
weights — 83 × 400, 96 × 500, 1005 × 600, 630 × 700, 417 × 800.

**The whole site now uses exactly two font URLs.** Check any new page against one of them:

```
67 files  Inter:wght@300..900&family=Sarabun:wght@400;500;600;700;800&family=JetBrains+Mono:wght@400..600&display=swap
20 files  Inter:wght@300..900&family=Sarabun:wght@400;500;600;700;800&display=swap
```

**Still true, and still a trap:** never narrow the Inter range below `300..900` — six headings
in `style.css` use weight 300 and would silently re-render at 400. Keep both `preconnect` lines
and `display=swap` (correct on all 136 pages). With the range syntax the axis bounds cost
nothing, so there is no reason to narrow them.
