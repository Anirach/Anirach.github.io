ทำความเข้าใจขอบเขตนี้

ผลโมเดลกับสิทธิ์เป็นข้อมูลคนละชุด ข้อเสนอ route ที่มั่นใจสูงไม่ได้อนุญาตให้ทำงานภายนอก และข้อความอ้างว่าคนอนุมัติแล้วไม่ใช่ approval record guard แบบ deterministic ตรวจชื่อ action จากชุดปิด ticket ที่รู้จัก คิวที่อนุญาต และ approval แยกที่ผูกกับ action และ release เดียวกัน

ผลกระทบทั้งหมดในแล็บเป็นการเขียน JSON ledger จำลอง ชื่อ demo-reviewer เป็น placeholder สำหรับสอน ไม่ใช่ระบบยืนยันตัวตน ledger แบบลำดับเดียวสาธิตการตรวจ idempotency แต่ไม่รับประกันเมื่อมีหลาย process พร้อมกัน ระบบจริงต้องมีผู้อนุมัติที่ยืนยันตัวตน audit ที่ป้องกันแก้ไข ที่เก็บข้อมูล durable แบบ atomic และ unique-key constraint ในฐานข้อมูล

approval key รวม release, ticket ID, ชนิด action และคิว การเปลี่ยนค่าใดทำให้ approval เดิมใช้ไม่ได้ จึงไม่เอาข้อเสนอ billing ที่ตรวจแล้วไปใช้ส่ง technical หรือใช้ข้าม release ได้ การ hash อย่างเดียวไม่ได้พิสูจน์ว่าใครอนุมัติ มันเพียงผูก record กับ payload เฉพาะในเดโมนี้

ลงมือทีละเจ็ดขั้น

ขั้นที่ 1

ตรวจ effectGuard ก่อนรัน actions ฟังก์ชันเริ่มจากปฏิเสธและจะคืน allow หลังเงื่อนไขโครงสร้างทุกข้อกับ approval แยกตรงกัน provider ไม่ได้รับ approval object ดังนั้นเนื้อหาที่โมเดลสร้างไม่สามารถตั้ง approved ให้ตัวเองผ่าน response schema

ขั้นที่ 2

รัน actions โดยไม่มี flag อนุมัติ ผลที่คาดคือ blocked พร้อม needs_human_approval และเส้นทางนี้ไม่ควรสร้างไฟล์ ledger ให้นับเป็นการทดสอบปฏิเสธที่สำเร็จ ไม่ใช่เดโมเสียที่ต้องหาทางข้าม

ขั้นที่ 3

รัน ticket เดิมพร้อมการอนุมัติเดโมอย่างชัดแจ้งและระบุ ledger ใหม่ โปรแกรมจะสร้างรายการจำลอง ไม่ใช่ request ไป help-desk API ดู simulation:true ก่อนตีความว่าคำว่า simulated หมายถึงเกิดงานภายนอกจริง

ขั้นที่ 4

รันคำสั่งที่อนุมัติเดิมกับ ledger เดิมอีกครั้ง ควรได้ duplicate แทนการเพิ่มผลซ้ำ นี่คือ contract ที่ตรวจเห็นได้สำหรับการรันซ้ำตามลำดับ อย่าสรุปว่าโค้ดนี้รองรับสอง process พร้อมกัน เพราะ implementation ระบุชัดว่าไม่ได้อ้างเช่นนั้น

ขั้นที่ 5

อ่าน test เปลี่ยนคิว ซึ่งสร้าง approval ที่ถูกต้อง เปลี่ยน queue แล้วคาดว่าจะถูกปฏิเสธ เหตุผลคือ approval ควรอนุญาต payload ที่ตรวจแล้ว ไม่ใช่ความตั้งใจคลุม ๆ ว่าให้โมเดลทำอะไรสักอย่างที่เป็นประโยชน์กับ ticket

ขั้นที่ 6

อ่าน test action ต้องห้าม ซึ่งเปลี่ยน kind เป็น refund และให้ confidence สูง guard ยังต้องปฏิเสธ เพราะ confidence เป็นหลักฐานเชิงความหมาย ส่วน allow-list ของ action เป็นขอบเขตสิทธิ์เชิงโครงสร้าง ไม่ควรรวมหน้าที่สองอย่างเข้าด้วยกัน

ขั้นที่ 7

ระบุช่องว่างก่อนใช้งานจริง เขียนว่าระบบ identity ที่เก็บข้อมูล transactional และหน้าจอ review ใดจะมาแทน placeholder จนกว่าจะทำและทดสอบส่วนเหล่านั้นเสร็จ ให้ใช้เพียง simulation หรือ shadow mode ผล benchmark โมเดลไม่สามารถปิดช่องว่างของ effect boundary ได้

ไฟล์และคำสั่งที่ใช้

โค้ดประกอบบน GitHub: ai-core-jev-tutorial · README. ใช้ repo เป็นทางหลักในการทำแบบฝึก ไฟล์ต่อไปนี้ตรึงกับรุ่นที่ทดสอบแล้ว src/effects.mjs · test/effects.test.mjs

เปิดไฟล์นี้เทียบกับ source ใน ZIP ก่อนแก้ ข้อความต่อไปนี้คือโค้ดที่ใช้ในโครงการจริง ไม่ใช่ pseudocode ผลโมเดลเป็น input ให้โค้ดตรวจและวางเส้นทางต่อ ไม่ใช่สิทธิ์ให้ข้ามด่านอนุมัติ

src/effects.mjs

import {createHash} from 'node:crypto';import {readFile,writeFile,mkdir} from 'node:fs/promises';import {dirname} from 'node:path';
import {QUEUES} from './contracts.mjs';
export function approvalKey(action,release) {return createHash('sha256').update(JSON.stringify([release,action.ticketId,action.kind,action.queue])).digest('hex');}
export function effectGuard(proposal,{knownIds,approval,release}) {
  const a=proposal.action;
  if(proposal.status!=='proposed'||!a||a.kind!=='route_ticket')return {allow:false,reason:'unsupported_or_unready'};
  if(!knownIds.has(a.ticketId)||a.ticketId!==proposal.ticketId||!QUEUES.includes(a.queue))return {allow:false,reason:'out_of_scope'};
  const key=approvalKey(a,release);
  if(approval?.key!==key||approval?.reviewer!=='demo-reviewer'||approval?.approved!==true)return {allow:false,reason:'needs_human_approval'};
  return {allow:true,key};
}
export async function simulate(proposal,context,ledger) {
  const gate=effectGuard(proposal,context);if(!gate.allow)return {status:'blocked',reason:gate.reason};
  let rows=[];try{rows=JSON.parse(await readFile(ledger,'utf8'))}catch(e){if(e.code!=='ENOENT')throw e}
  if(rows.some(r=>r.key===gate.key))return {status:'duplicate',key:gate.key};
  rows.push({key:gate.key,release:context.release,...proposal.action,simulation:true});
  await mkdir(dirname(ledger),{recursive:true});await writeFile(ledger,JSON.stringify(rows,null,2)+'\n');return {status:'simulated',key:gate.key};
}
// Teaching ledger: serial, single-process only. Production requires authenticated
// approvals, a transactional unique key and atomic durable writes.

ตรวจผลที่ควรได้

เมื่อเริ่มจาก ledger ใหม่ คำสั่งสามครั้งควรคืน blocked, simulated และ duplicate ตามลำดับ ถ้าเปิดบทเรียนซ้ำโดยมี ledger อยู่แล้วอาจเริ่มที่ duplicate ให้ใช้ชื่อไฟล์ใหม่เมื่อต้องการทำลำดับครั้งแรก ไม่มีการติดต่อกับลูกค้าหรือทำธุรกรรมการเงินในโครงการนี้

ตรวจชื่อ test และเส้นทางปฏิเสธด้วย อย่าดูเพียง exit code หรือ label สุดท้าย ข้อมูลที่ไม่ทราบต้องยังระบุว่าไม่ทราบ และรายงานทุกชิ้นต้องแยกผลจำลองออกจากข้อมูลที่วัดจริง

แก้ปัญหาเมื่อผลไม่ตรง

ถ้ามีผลเกิดก่อน effectGuard แปลว่าสถาปัตยกรรมผิดแม้ test ของ guard ผ่าน ถ้ามีรายการซ้ำเมื่อทำงานพร้อมกัน ให้ใช้ที่เก็บข้อมูลแบบ transactional ไม่ใช่เพิ่ม sleep ถ้าโหลด approval จากผลโมเดล ต้องแยกไปเป็นช่องทางที่แอปควบคุมและเชื่อถือได้

หากเปิดบทเรียนผ่าน Python http.server ให้ใช้ลิงก์ .html ที่ท้ายตอนเมื่อจำเป็น ลิงก์ chip แบบไม่มีนามสกุลในแถบซีรีส์อาศัยการ resolve ของ GitHub Pages และเป็นข้อจำกัด preview ที่มีอยู่เดิม ไม่ใช่ปัญหาในโค้ด Node

เปลี่ยนหนึ่งอย่างแล้วทดสอบ

อนุมัติข้อเสนอหนึ่งชุดแล้วเปลี่ยน release identifier ตรวจว่า approval key เดิมใช้ไม่ได้ จากนั้นอธิบายว่าผู้อนุมัติที่ยืนยันตัวตนกับฐานข้อมูล transactional จะมาแทน placeholder อย่างไร อย่าเรียก JSON ledger ที่ใช้สอนว่าเป็นบริการอนุมัติพร้อมใช้งานจริง

ทำการแก้ไขในสำเนาทดลอง เก็บไฟล์ต้นฉบับไว้เทียบ แล้วคืนค่าก่อนเริ่มตอนถัดไป หากทดลองกับ provider จริงภายหลัง ให้สร้าง experiment record ใหม่แทนเขียนทับผลเดิม

How this boundary works

Model output and permission are different data. A high-confidence route proposal does not authorize an external action, and text claiming that a reviewer approved cannot become an approval record. Our deterministic guard checks a closed action name, a known ticket, an allowed queue and a separate approval bound to the exact action and release.

All effects in the lab are simulated JSON-ledger entries. The demo-reviewer identity is a teaching placeholder, not authentication. The serial ledger demonstrates an idempotency check but has no transactional concurrency guarantee. A production service needs authenticated reviewers, tamper-resistant audit, atomic durable storage and a unique-key constraint enforced by its database.

The approval key includes release, ticket ID, action kind and queue. Changing any of those invalidates the approval. This prevents a reviewed billing proposal from being reused for a technical route or another release. Hashing alone does not establish who approved; it merely binds the approval record to a specific payload in this demonstration.

Seven practical steps

Step 1 — Inspect effectGuard before running actions

Inspect effectGuard before running actions. It begins with refusal and returns allow only after every structural condition and the separate approval match. The provider never receives the approval object, so generated content cannot set its own approved flag through the response schema.

Step 2 — Run actions without the approval flag

Run actions without the approval flag. The expected result is blocked with needs_human_approval, and no ledger file should be created by that path. Treat this as a successful refusal test, not as a broken demonstration to be bypassed.

Step 3 — Run the same ticket with explicit demonstration approval and a fresh named ledger

Run the same ticket with explicit demonstration approval and a fresh named ledger. The program creates a simulation entry, not a help-desk API request. Inspect simulation:true before interpreting the word simulated as an action that happened outside the lab.

Step 4 — Repeat the exact approved command against that ledger

Repeat the exact approved command against that ledger. It should return duplicate rather than append another effect. This is the observable contract for serial reruns. Do not infer that the same code handles two simultaneous processes; the implementation explicitly does not make that claim.

Step 5 — Read the changed-queue test

Read the changed-queue test. It makes a valid approval, alters the queue and expects refusal. This matters because approvals should authorize the reviewed payload, not a vague intention such as let the model do something useful with this ticket.

Step 6 — Read the forbidden-action test

Read the forbidden-action test. It changes kind to refund and supplies high confidence. The guard still denies it. Confidence is semantic evidence; the action allow-list is a structural permission boundary. Their responsibilities should not be merged.

Step 7 — Name the production gap before continuing

Name the production gap before continuing. Write down which identity system, transactional store and review interface would replace the placeholders. Until those decisions are implemented and tested, keep the project in simulation or shadow mode. A model benchmark does not close an effect-boundary gap.

  if(rows.some(r=>r.key===gate.key))return {status:'duplicate',key:gate.key};
  rows.push({key:gate.key,release:context.release,...proposal.action,simulation:true});
  await mkdir(dirname(ledger),{recursive:true});await writeFile(ledger,JSON.stringify(rows,null,2)+'\n');return {status:'simulated',key:gate.key};
}
// Teaching ledger: serial, single-process only. Production requires authenticated
// approvals, a transactional unique key and atomic durable writes.

Verify the expected behavior

With a fresh ledger, the three commands should return blocked, simulated and duplicate in order. Re-running a chapter with an existing ledger may start at duplicate; use a new filename to reproduce the first-run sequence. No customer contact or monetary action is implemented.

Read the named tests and refusal paths, not just the exit code or final label. Unknown values must remain unknown, and every report must distinguish simulation inputs from real measurements.

Troubleshooting

If an effect occurs before effectGuard, the architecture is wrong even if tests for the guard pass. If duplicate entries appear in concurrent execution, use a transactional storage design rather than adding a sleep. If approval is loaded from model output, separate it into a trusted application-owned channel.

When previewing with Python http.server, use the .html continuation links below when needed. Extensionless series chips rely on GitHub Pages resolution; that documented preview limitation is separate from the Node example.

Change one thing, then test

Approve one proposal, change its release identifier, and check that the old approval key no longer authorizes it. Then describe how an authenticated reviewer and transactional database would replace the demo placeholders. Do not call the teaching JSON ledger a production approval service.

Make changes in a disposable copy, retain the reference files for comparison, and restore them before the next chapter. If you later use a real provider, create a new experiment record rather than overwriting the fixture transcript.
